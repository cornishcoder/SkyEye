## Event timeline and shot-clip path

Treat events as the shared evidence layer for the live display, later match-state inference, and shot clips. Keep perception events independent of `GameState`: a table observation or candidate does not by itself change the shooter, turn, foul, score, or frame result.

Every completed sequential full analysis pass must produce one timestamped observation record with exactly one `checkOutcome`: for example `baseline_pending`, `clear_unchanged`, `movement_observed`, `obstructed`, `layout_uncertain`, `layout_change_pending`, or a settled transition. This answers “what did this check conclude?” even when the answer is “nothing changed.” The typed event stream is a separate layer: it records meaningful transitions and before/after evidence, rather than duplicating a `still` event for every unchanged frame. A failed or unavailable pass must also be recorded as a failure/stale-source outcome, never silently omitted or represented by the prior result.

### State-machine boundary

Use two processing stages, with one canonical state history:

1. **Table event interpretation** consumes each fresh Live Detect observation, its source time, quality and layout, plus the last supported baseline. It tracks the table-analysis phase (baseline, activity, obstruction/uncertainty, settling, settled) and emits evidence-backed table events such as movement, no-pot observed, possible pot settled, balls returned, or rack detected. These remain perception observations/candidates and do not choose a shooter or declare legality.
2. **Match-state reduction** applies only accepted table facts together with player-declared or otherwise supported rule facts. The existing `SkyEye.GameState` append-only history and `GameReducer` remain authoritative for `TableState`, `FrameState` and `MatchState`; do not add another persisted table inventory or a parallel match reducer.

`TableMotionStateMachine` remains diagnostic-only through `TableMotionFeed`; `LiveDetectTableEventTracker` now owns Live Detect's stateful, image-free transition reducer, coordinating `StableTableChangeTracker` and `LiveDetectCountCandidateTracker` behind one observation-in/event-batch-out seam. `ShellLiveDetect` supplies each fresh observation and performs logging/clip I/O. The reducer does not mutate canonical state: `GameReducer` still owns `GameState` table and match projections. Saved code39 logs replay through the extracted reducer below; those are detector-output replays, not a new live acceptance or a rerun of vision.

| Stage | Event evidence | Meaning and limits |
| --- | --- | --- |
| Baseline | `rack_detected` or `settled_layout_observed`, with source timeline, frame ID/source PTS, inventory, positions, and quality | A complete packed rack can establish a new inventory baseline. A spread layout can also establish a baseline; a match is not required. |
| Activity | `activity_started` / `activity_ended`, with source-time bounds; `movement_observed`; `obstruction_started`, `layout_uncertain`, and `clear_view_returned` as quality transitions | Movement can delimit a shot attempt. Obstruction means the layout is temporarily unreadable; it is not evidence of a pot, a miss, or a shot outcome. An activity that returns to its prior layout is logged separately; save a clip only if movement was observed. If motion coverage is missing or interrupted, retain an unknown boundary. |
| Settled after-state | `settled_layout_baseline` and settled layout changes, backed by repeated fresh, clear, matching layouts | Compare the new layout against the last clear baseline. Preserve both inventories, positions, frame IDs and source PTS so the transition can be replayed and reviewed. |
| Derived table event | `possible_pot`, `possible_pot_settled`, `balls_returned_candidate`, `no_pot_observed`, `settled_layout_change_unclassified`, `settled_inventory_change`, or `rack_detected` | A decrease is a pot candidate only after clear confirmation. Same inventory plus meaningful moved positions after independently observed movement establishes a no-pot observation; obstruction alone cannot produce one. A stable layout change without a movement signal remains unclassified. Events retain before/after positions and source PTS for replay. These observations do not claim a legal miss or infer the turn. |
| Match projection | Accepted pot / no-pot / foul / turn / rack decisions projected into canonical `GameState` | Rules need shooter, groups, contact/legality and cue-ball facts where applicable. Keep unresolved facts pending; visual inventory alone must not advance the turn. |
| Shot clip | Link a saved camera clip to the activity and settled-state event IDs, including intended pre-roll/post-roll and verified source-time window | Aim to include the player's line-up, movement, and balls coming to rest. Event timestamps can select the window only after camera PTS-to-clip mapping is verified. Preserve the wider source clip and event metadata until exact trimming is proven. |

The camera save command accepts recent windows of 30, 60, 120, 300, or 600 seconds. The new Live Detect path removes periodic 30-second saves and requests a clip for a non-rack movement activity that settles as a no-pot observation, a possible pot, or a mixed inventory change. An obstruction-only activity or an unclassified layout change does not produce a shot clip. It chooses the smallest supported window that includes a 20-second lead-in, the settled event plus 2 seconds of post-roll, and a 4-second save-boundary margin. Each clip-save record links the activity ID and intended source-time window to the clip recording origin, then reports whether that origin covers the full window. This saves event-driven clips rather than exact trimmed shots. Validate decoded-frame PTS against the clip origin and measure whether the lead-in includes normal player line-up before claiming full shot coverage. The previous periodic behavior remains in historical code39 evidence only.

### Acceptance sequence

1. Establish a clear spread or rack baseline and log its timestamped positions.
2. Capture a no-pot shot: observe activity, any obstruction, then a clear settled same-inventory layout with positions moved. Emit a no-pot observation only if all evidence supports that chain; otherwise retain an unknown/layout-change result.
3. Capture a pot and a cue scratch/return with the same event chain; verify count changes and location evidence do not turn a hand occlusion into a pot.
4. Re-rack in the same Live Detect run. Confirm the rack event replaces the current baseline while retaining the preceding event history.
5. Join each event window to saved footage using source timeline/PTS and frame anchors. Review that the selected clip includes line-up, action, and rest; adjust pre-roll/post-roll from measured examples.
6. Only after event and clip correlation is verified, feed supported outcomes through existing rules and canonical `GameState`. Keep rule facts the camera cannot see as unknown or player-confirmed.
