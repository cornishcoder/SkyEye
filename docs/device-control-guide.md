## Identify balls overlay shortcut

Source implementation only (not yet installed or physically checked): on Home, **Identify balls** appears only while Live Detect is running. Its handler is `Routes.razor` → `ToggleIdentifyBalls()` → `ShellSession.ToggleIdentifyBallsAsync()`; the toggle publishes an additive `TableScene` identity layer through `PlayerBridge.SetIdentityScene`, using the latest accepted `VisionResult.Balls` from `ShellLiveDetect.cs`. It does not start capture or run another detector. It requires an active calibrated live view and running Live Detect. The button's accessible name is **Show ball identity overlay** while off and **Hide ball identity overlay** while on; `aria-pressed` and the visible **Identities off/on** text report its state. When on, the phone video shows per-frame detector class labels (R red, Y yellow, 8 black, C cue, ? other), the calibrated cloth boundary and cyan pocket centres labeled P1–P6. These are colour classes, not persistent identities such as R1/Y1; labels are staggered but can still overlap in a tightly packed rack. The status beneath Live Detect reports the rendered frame ID, capture time, count and uncertainty/obstruction when present. Check those values against the matching timestamp/frame in `GET /api/live-detect-log?limit=<1..2000>`. Stopping Live Detect clears the overlay and hides the button. This shortcut does not choose a Cast route or change TV playback; a TV identity overlay is deferred because its active compositor is a separate scene path.

This text is owned by `ShellLiveDetect.cs`; frame-log schema 12 records `baselineMatchSamples` and `settledBaselineMatchesCurrent`. A transient uncertain or obstructed frame retains the previous baseline; a matching clear return begins/continues the stable-sample check, and does not create a pot/miss event by itself. ## Read-only live diagnostics

The Production Hybrid shell exposes a read-only live vision dashboard when it is running. Its URL is shown under **Settings → Table analysis and shot display → Live vision dashboard**. The displayed browser dashboard and these GET endpoints inspect current state without sending a match command:

- `GET /api/snapshot` returns the latest sampled frame, frame age and sequence, detector counts/warnings, calibration ID, tracked table and whether the canonical game table is current.
- `GET /api/frame?sessionId=<id>&sequence=<n>` returns the exact JPEG associated with that snapshot. Use the same session ID and sequence; if it responds `409` because a newer frame arrived, fetch a new snapshot and inspect that one.
- `GET /api/live-match` returns a read-only current match/game summary.
- `GET /api/live-detect-log?limit=<1..2000>` returns recent image-free Live Detect frame, typed table-event, run-event and clip-save records, including a classification for every full check, event timestamps, camera timeline/PTS, before/after inventories and positions, activity IDs, and clip source-window coverage.

For a live analysis, check `frame.capturedAt`, `frame.frameAgeMs`, `detection.uncertain`, `detection.obstructed`, `detection.balls`, the observation timestamp/outcome, `trackedTable.settled`/`occluded`/`confirmed`, and `gameTableCurrent`. A calibration ID only shows that calibration exists; it does not make an old table observation current. `Physics available` is also not proof of a correct inventory.

The live dashboard has no general Production command endpoint. Do not use POST routes such as `/api/live-match/review` or any `/api/scenario/*` route for diagnosis; review routes can change canonical state, while Scenario Lab routes edit a disposable match. The Production package and dashboard were verified on this device; do not assume a separately installed Lab package has the same runtime or journal state.

### Sky shot samples

The Home header calls [`ShellShotSamples.cs`](../src/SkyEye.Companion.Hybrid/ShellShotSamples.cs) `ToggleSampleCollection`, which uses the same preference and handler as Sky's `set_sample_collection` tool. The feature starts off by default. Enable it explicitly, start a normal live or dark recording and connect Sky; no match or calibration is required. While it is enabled, Sky can submit a player's ordinary completed-shot report such as “just potted a red” or “missed that one”. Home shows `Saving sample…` followed by the actual success, failure, or unknown result; Sky can read the same result through `get_sample_collection`. A second report while one is saving is rejected as busy, with no new clip requested. Turning the mode off stops new admissions; an already admitted request continues.

Each sample keeps the original speech transcript, explicitly tagged `player-reported`, and optional suggested categories and notes copied from that transcript. Transcription and categorisation can be wrong; these are player-reported training notes, not vision observations or match rulings. The app journals the report before sending the existing `SaveClip` command and links it to the acknowledged clip ID, hash and actual duration, plus the camera-provided source origin when available. A saved observation's calibration, configuration and source timestamp are context only, with their own capture time; the spoken report is not mapped to a precise camera timestamp. The companion converts the desired five-second span to a same-timeline source range after its two-second settling window; the camera selects the intersecting segments, starts at the preceding decodable keyframe, and trims at the requested end PTS. The keyframe can add up to one segment of lead-in, while a short or missing retained history may leave the requested start uncovered. The save receipt preserves the requested range, actual origin, duration, hash, and whether the saved clip covers the range; verify decoded-frame coverage before claiming an exact five-second sample.

On **Open clips**, expand **Player-reported sample** beside the matching camera clip to inspect its transcript and extracted excerpts. **Share sample metadata** opens the Android share chooser for that sample's JSON; the clip's usual download/share actions remain separate. Metadata is private to this phone until deliberately shared. A pending report interrupted after the clip acknowledgement can be recovered from the durable save receipt on app restart. An unacknowledged save remains unknown and is not repeated automatically. A failed local metadata update is reported separately from a saved camera clip. The shortcut never starts capture; after any bounded live check use **End recording session**, verify `/status` is `Stopped`, and return Home to **Start live session**.

For an explicit spoken **“save the last five seconds”**, Sky can send `save_recent_clip` with `seconds=5`; the companion translates the convenience duration to a source-time range before calling the camera. With sample collection enabled and matching speech text, it journals that text against the same operation and marks it partial when no completed transcript was received. If speech text is unavailable, the explicit clip request can still proceed and reports that sample metadata was not attached. A player can ask Sky to add words to the latest sample; `get_sample_collection` exposes its operation ID and `add_sample_details` appends a separately transcribed, player-reported statement to that sample, including while the clip save is pending. It does not create a second clip or change match state. The recorded range and actual saved origin are available for post-save coverage review.

If an existing clip was saved without sample metadata, select that specific camera clip and use **Add player report**, enter the player's actual words, then **Save player report**. This attaches the report only if the phone has a unique durable save receipt matching the clip ID and checksum. Sky can also use `get_saved_clips` and `attach_report_to_saved_clip` when the player identifies the clip; it must ask when the selection is ambiguous. Neither path starts recording or invents an exact shot time. Typed reports are marked `typed`; Sky can retain streamed transcript words when a completed transcript event is unavailable, and marks those words `partial` so they are not presented as a complete quotation.

Sky's neutral **“what is on the table?”** request should use `get_table_state`: it reads the live calibrated perception layout and its `settled`, `occluded`, `confirmed`, `outcome`, `motion`, and freshness fields without requiring a match. `get_match_state` is the canonical match ledger and its table is match-bound. `gameTableCurrent` says whether the canonical GameState table image is current live evidence for its active game frame; `get_match_state.table.fresh` additionally applies the age limit. It is expected to remain false when there is no active match frame, even if a live verifier successfully published a clear observation. The motion diagnostic feed can still report image motion without a match, but its activity lifecycle reports diagnostic-only and does not claim match readiness. To observe a movement-to-settled transition without a match, use two bounded **Show candidate shots** checks with the existing status readback: one while a single ball is moving (expect `Moving`/unsettled), then one after it stops (expect `Ready`/settled if detection is clear). Do not use `gameTableCurrent` as the perception readiness signal in that test.
