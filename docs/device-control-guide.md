`Start live session` is the normal setup route. Source code in [`ShellCameraControls.cs`](../src/SkyEye.Companion.Hybrid/ShellCameraControls.cs) sequences connection to the saved camera when needed, claims host control only when available, starts capture if needed, then opens the live phone view. It verifies that the camera is active and the live source opened. A previous 2026-10-25 run used the direct home-grid action successfully; the screen reported **“Live session · Camera active”** and **“Physics available.”** On each run, inspect the current tile and live state: press `Start live session` once only when the tile shows that label and the camera is confirmed inactive. If it shows `End recording session`, leave it alone. The implementation rejects a second start while a session is active.

The Home shot shortcut is part of the same main-action grid. Its exact accessible name is `Show candidate shots`; while choices are being displayed it changes to `Hide candidate shots`, and the pressed state reports whether choices are shown. During a request it becomes `Checking candidate shots` and disables itself. The visible tile text is `Show shots`, `Hide shots` or `Checking`.

The Home Live Detect action is implemented in [`Routes.razor`](../src/SkyEye.Companion.Hybrid/Components/Routes.razor) by `ToggleLiveDetect`, which calls [`ShellLiveDetect.cs`](../src/SkyEye.Companion.Hybrid/ShellLiveDetect.cs) `ToggleLiveDetectAsync`. Its accessible name is `Start live detect`, `Stop live detect`, `Finishing live detect`, or `Live detect unavailable: …`; the visible tile says `Live detect`, `Detecting`, or `Stopping`. It requires the current live session to be active, the table calibrated, no edit or competing analysis/diagnostic, and candidate shots hidden. It never starts capture. It does not require a match and does not write detector output to canonical `GameState`. It pauses an existing sequential diagnostic sampler while running and resumes it afterwards when still available.

For the image transforms, candidate stages, coordinate spaces and still-table/event handoff, see the [Live Detect pipeline flow chart](live-detect-pipeline.md). In particular, the analyzer applies the saved perspective correction to its own decoded-frame copy; the live-view screen transform is a separate rendering path.

Each loop iteration awaits `TableAnalysisSession.UpdateAsync` before requesting the next frame. This gives one full 800px `VisionAnalyzer` pass at a time and reads the newest available exact-paired decoded frame when each pass finishes; it does not queue frames or run shot planning. Every full check is retained as a timestamped frame record with a `checkOutcome` such as `clear_unchanged`, `movement_observed`, `obstructed`, `layout_uncertain`, `inventory_change_pending`, or a settled transition. Typed table events are emitted on state transitions rather than duplicating an unchanged event on every frame. Home shows the latest detector count by colour, detector uncertainty/obstruction, frame age and measured full-pass time. `Possible pot` uses [`LiveDetectCountCandidateTracker`](../src/SkyEye.Companion.Hybrid/LiveDetectCountCandidateTracker.cs) to retain the last clear inventory across unclear frames for the current camera timeline, then requires two matching eligible counts within five seconds with a named-colour decrease and no count increase or unknown-colour change. The retained comparison point is historical evidence, not the current table reading: only the latest accepted frame is shown as the current inventory. A camera timeline change resets it. Layout uncertainty and obstruction cannot confirm a candidate; broad advice uncertainty alone does not exclude a clear cue/black-absent layout. This reports a count change only: it does not confirm a pocket, write to match history, or prove table readiness. A transient analysis exception is logged and retried up to three consecutive failures; the run then stops with a visible failure status. Run-start, retry, failure and stop events include the latest frame ID/source timestamp where available.

Live Detect no longer saves a clip on a 30-second timer. After a non-rack movement activity reaches a clear settled result, it requests one saved clip linked to that activity when the result is a no-pot observation, a possible pot, or a mixed inventory change. A same-inventory layout change without independently observed movement remains unclassified and does not become a no-pot event. An obstruction by itself never implies a shot or causes a no-pot event. The intended window begins 20 seconds before the first observed movement/obstruction and ends two seconds after the settled event; the requested camera duration rounds that range plus a four-second boundary margin up to the next supported duration (30, 60, 120, 300 or 600 seconds). The camera's existing host-authorized `SaveClip` command still saves a recent window rather than an exact trim. The log links the activity ID and intended source-time range to the clip's recording origin and records whether that origin covers the window. Exact PTS-to-clip coverage and adequate line-up lead-in still need physical acceptance. An event save already in progress is allowed to finish when Live Detect is stopped; ending the recording session waits for it before stopping the camera. Each event clip creates a durable camera clip and uses camera storage; clips are not cast to the TV. Home reports the latest event-clip result and count.

Tap `Stop live detect` to stop the loop; ending the recording session, losing the live source/calibration, or pausing SkyEye also cancels it. After ending recording, verify `/status` is `Stopped` and Home shows `Start live session`.

Current-source event handling confirms repeated inventory changes without using obstruction as pot evidence. **Rack detected** requires the analyzer's complete packed-rack evidence and a full 7-red/7-yellow/black/cue inventory on repeated results. A full spread inventory alone is insufficient. Every full Live Detect pass records a typed `checkOutcome`; the image-free log also appends source-stamped table events for stable baselines, movement/activity, obstruction or uncertainty, clear-view return, inventory candidates and settled layout transitions. Same-inventory movement becomes **No pot observed** only when movement was independently observed; a stable layout difference without that signal remains unclassified. Neither event infers shooter, legality or turn. The Home event list retains up to twelve recent entries across rack changes, and the source-stamped log retains the bounded history. Code40's stationary 12-ball pass physically confirmed the baseline and repeated `clear_unchanged` outcomes; shot, obstruction, pot and re-rack transitions still need physical acceptance. Code41 corrects the event-clip operation count while preserving old clips. Clear cue/black-absent layouts remain admitted independently of advice uncertainty; ambiguous layout and obstruction still block inventory events. The [Live Detect plan](live-detect-plan.md) records current evidence and remaining acceptance.

Every analyzed frame, run status, typed table event and event-linked clip-save request/acknowledgement is appended to an image-free JSONL log at `GetExternalFilesDir(null)/live-detect/live-detect.jsonl`. Frame records include wall-clock record/capture times, camera connection and media generation, frame ID, source and presentation timestamps, surface timestamp, timeline, calibration ID, counts, normalized ball coordinates, confidence, warnings and `checkOutcome`. Clip-save records have a shared `runId`, operation ID, activity/event IDs, intended PTS window, request and completion times, clip ID/name/duration/created time/size/hash, and nearest frame ID/source timestamp anchors on both sides. Run events record start/stop/retry/failure, a safe exception type, and the latest frame anchor. Pair records using `runId` and clip-save `operationId`; the request-side frame/source timestamp is the useful source-time anchor, but exact camera-clip-to-decoded-frame time mapping has not yet been independently validated.

Frame-log schema version 2 separates `uncertain` (the broader advice gate) from `layoutUncertain` (whether the visible layout itself can support inventory/readiness). A cue/black-absent layout can therefore be logged as layout-clear while advice remains unavailable; unknown balls, obstruction, weak boundaries and similar layout evidence remain blocked.

The log survives an app process restart and in-place app update. The read-only `GET /api/live-detect-log?limit=500` endpoint returns recent records (maximum 2,000); `GET /api/snapshot` reports retained counts and the first/last log timestamps. These endpoints are available while the local vision dashboard is running. For later retrieval even when the dashboard is off, pull the app-specific file from the Pixel 11 with ADB: `adb pull /sdcard/Android/data/uk.co.skyeye.companion/files/live-detect/live-detect.jsonl`. The log is bounded to 2,000 recent records or 4 MiB and stores no images; the actual saved video remains in the camera's clip library.

### Keep live capture short

Live capture uses battery on the mounted Pixel 10 camera even if the Pixel 11 companion is backgrounded or closed. Keep the session active only while an authorized task is actively acquiring live evidence. At the first safe boundary after a bounded capture, before a long build or offline replay, while waiting, or when finishing, use the home tile **`End recording session`**. It sends the existing camera `Stop` action and ends phone playback/analysis; backgrounding or closing the companion does not stop camera recording. This preserves saved clips. The menu remains pinned by default so the table does not expand to fullscreen during playback; if the user deliberately chooses **`Unpin menu panel`**, the existing five-second fade can hide the controls. On code 11, an advertised tap after the video expanded did not visually restore the controls; one swipe-up did. Pin the panel again to keep the controls visible. Accessibility bounds can change with the selected pin state, so use only a fresh screenshot and the center of the currently visible, correctly labelled control once; do not reuse stale bounds. If the stop tile is not visibly reachable, ask the user to press **`End recording session`** rather than continue tapping or swiping. Verify `GET http://<camera-address>:8765/status` reports `state: "Stopped"`; `armed: true` or a retained host does not mean capture is still running. Return the companion to Home and confirm **`Start live session`** is shown. If the stop is not confirmed, inspect current status and recover through the existing controls before leaving the device.

Restart capture only when the authorized work again needs live frames, using the normal Home route. Perception stillness checks do not require a match; do not start a match just to run them. Do not interact with Cast or the TV while the user is watching.

Those labels show session readiness, not detector accuracy or a fresh settled table. Use the diagnostic snapshot below to check the frame and current detection.

The live video header's small **`CAM N%`** gauge reports the mounted camera's battery when a fresh camera status is available. Unknown status appears as **`CAM —`** and is exposed to accessibility as an unknown level; it is never shown as 0%. The camera API does not expose charging state. At the latest stop check (26 October, revision 127), `/status` reported `Stopped`, eight clips and zero viewers; Home showed the `Start live session` action, the panel was `Pinned`, and Cast was untouched. `armed: true` did not mean it was recording.

## Read-only live diagnostics

The Production Hybrid shell exposes a read-only live vision dashboard when it is running. Its URL is shown under **Settings → Table analysis and shot display → Live vision dashboard**. The displayed browser dashboard and these GET endpoints inspect current state without sending a match command:

- `GET /api/snapshot` returns the latest sampled frame, frame age and sequence, detector counts/warnings, calibration ID, tracked table and whether the canonical game table is current.
- `GET /api/frame?sessionId=<id>&sequence=<n>` returns the exact JPEG associated with that snapshot. Use the same session ID and sequence; if it responds `409` because a newer frame arrived, fetch a new snapshot and inspect that one.
- `GET /api/live-match` returns a read-only current match/game summary.
- `GET /api/live-detect-log?limit=<1..2000>` returns recent image-free Live Detect frame, typed table-event, run-event and clip-save records, including a classification for every full check, event timestamps, camera timeline/PTS, before/after inventories and positions, activity IDs, and clip source-window coverage.

For a live analysis, check `frame.capturedAt`, `frame.frameAgeMs`, `detection.uncertain`, `detection.obstructed`, `detection.balls`, the observation timestamp/outcome, `trackedTable.settled`/`occluded`/`confirmed`, and `gameTableCurrent`. A calibration ID only shows that calibration exists; it does not make an old table observation current. `Physics available` is also not proof of a correct inventory.

The live dashboard has no general Production command endpoint. Do not use POST routes such as `/api/live-match/review` or any `/api/scenario/*` route for diagnosis; review routes can change canonical state, while Scenario Lab routes edit a disposable match. The Production package and dashboard were verified on this device; do not assume a separately installed Lab package has the same runtime or journal state.

### Sky shot samples

The Home header calls [`ShellShotSamples.cs`](../src/SkyEye.Companion.Hybrid/ShellShotSamples.cs) `ToggleSampleCollection`, which uses the same preference and handler as Sky's `set_sample_collection` tool. The feature starts off by default. Enable it explicitly, start a normal live or dark recording and connect Sky; no match or calibration is required. While it is enabled, Sky can submit a player's ordinary completed-shot report such as “just potted a red” or “missed that one”. Home shows `Saving sample…` followed by the actual success, failure, or unknown result; Sky can read the same result through `get_sample_collection`. A second report while one is saving is rejected as busy, with no new clip requested. Turning the mode off stops new admissions; an already admitted request continues.

Each sample keeps the original speech transcript, explicitly tagged `player-reported`, and optional suggested categories and notes copied from that transcript. Transcription and categorisation can be wrong; these are player-reported training notes, not vision observations or match rulings. The app journals the report before sending the existing `SaveClip` command and links it to the acknowledged clip ID, hash and actual duration, plus the camera-provided source origin when available. A saved observation's calibration, configuration and source timestamp are context only, with their own capture time; the spoken report is not mapped to a precise camera timestamp. The camera's installed save API accepts a minimum of 30 seconds, selected on segment boundaries. The desired sample span is five seconds, but the app currently requests the shortest supported 30-second camera clip after a two-second settling window measured from the latest accepted transcript text; it cannot promise an exact five-second trim or prove the shot is inside. Short buffer history may yield a shorter clip. The actual duration and available source origin are preserved rather than inferred.

On **Open clips**, expand **Player-reported sample** beside the matching camera clip to inspect its transcript and extracted excerpts. **Share sample metadata** opens the Android share chooser for that sample's JSON; the clip's usual download/share actions remain separate. Metadata is private to this phone until deliberately shared. A pending report interrupted after the clip acknowledgement can be recovered from the durable save receipt on app restart. An unacknowledged save remains unknown and is not repeated automatically. A failed local metadata update is reported separately from a saved camera clip. The shortcut never starts capture; after any bounded live check use **End recording session**, verify `/status` is `Stopped`, and return Home to **Start live session**.

For an explicit spoken **“save the last five seconds”**, Sky can send `save_recent_clip` with `seconds=5`; the companion requests the camera's supported 30-second save and reports the actual result rather than refusing five seconds. With sample collection enabled and matching speech text, it journals that text against the same operation and marks it partial when no completed transcript was received. If speech text is unavailable, the explicit clip request can still proceed and reports that sample metadata was not attached. A player can ask Sky to add words to the latest sample; `get_sample_collection` exposes its operation ID and `add_sample_details` appends a separately transcribed, player-reported statement to that sample, including while the clip save is pending. It does not create a second clip or change match state. The five-second request is still not an exact trim, and actual shot coverage remains unverified.

If an existing clip was saved without sample metadata, select that specific camera clip and use **Add player report**, enter the player's actual words, then **Save player report**. This attaches the report only if the phone has a unique durable save receipt matching the clip ID and checksum. Sky can also use `get_saved_clips` and `attach_report_to_saved_clip` when the player identifies the clip; it must ask when the selection is ambiguous. Neither path starts recording or invents an exact shot time. Typed reports are marked `typed`; Sky can retain streamed transcript words when a completed transcript event is unavailable, and marks those words `partial` so they are not presented as a complete quotation.

Sky's neutral **“what is on the table?”** request should use `get_table_state`: it reads the live calibrated perception layout and its `settled`, `occluded`, `confirmed`, `outcome`, `motion`, and freshness fields without requiring a match. `get_match_state` is the canonical match ledger and its table is match-bound. `gameTableCurrent` says whether the canonical GameState table image is current live evidence for its active game frame; `get_match_state.table.fresh` additionally applies the age limit. It is expected to remain false when there is no active match frame, even if a live verifier successfully published a clear observation. The motion diagnostic feed can still report image motion without a match, but its activity lifecycle reports diagnostic-only and does not claim match readiness. To observe a movement-to-settled transition without a match, use two bounded **Show candidate shots** checks with the existing status readback: one while a single ball is moving (expect `Moving`/unsettled), then one after it stops (expect `Ready`/settled if detection is clear). Do not use `gameTableCurrent` as the perception readiness signal in that test.
