# O02 bounded motion feed and ROI measurements

7 October 2026. This slice adds an explicitly enabled source-scoped motion feed and bounded native fixed-region measurements. It is a foundation for O03/O04, with no canonical ball identity, shot boundaries or automatic GameState mutation. The normal release includes the implementation but starts no motion feed. Its developer enablement endpoint is present only in opt-in performance builds.

## Delivered behavior

`TableMotionFeed` owns one active frame and one replaceable latest frame. Pending ownership is released before another bitmap is acquired, so even transient acquisition stays within two image leases. A native metadata-only candidate query avoids another bitmap copy for repeated source frames and preserves a valid pending frame when polling faster than the decoder. Candidate identity is an allocation hint; the actual pixel copy still requires O02's exact surface timestamp receipt and before/after fencing.

The source, recording timeline, decoder generation, calibration reference and dimensions are frozen for each run. Changes terminate the run. Duplicate/backwards receipts, stale frames and late worker results are refused. Source PTS determines delta time; gaps over 125 ms reset motion history. Stopping disposes pending ownership immediately, waits for active processing and discards its late result. Worker/acquisition failure and cancellation drain the same ownership. A result that ages beyond admission bounds cannot advance processor history. Core tests also cover an acquisition that ignores cancellation and returns late.

`RoiMotionProcessor` accepts at most sixteen fixed pixel regions, each 32–256 pixels on either side. It crops the native bitmap before grayscale OpenCV conversion, retaining only previous gray ROIs. No full-frame Mat, JPEG, colour/Hough analysis or detector loop is introduced. Forward/backward pyramidal Lucas-Kanade feature flow uses bounded features, error/return consistency, image-bound checks and displacement agreement. Weak texture, occlusion and inconsistent evidence remain unresolved. Measurements are image-pixel displacement/velocity per source second, not ball coordinates, pot proposals or calibrated confidence. Fixed regions are not recentered tracks; region IDs are temporary sampling slots.

The implementation uses the existing OpenCV 4.14.0 native library and exposes only its needed video tracking bindings. Bulk coordinate reads remove the per-point JNI field traffic found in the initial benchmark. No upstream source code is copied. [OpenCV's tracking API](https://docs.opencv.org/4.13.0/dc/d6b/group__video__track.html) documents the status/error outputs and source-image requirements; the repository's pinned native binding is exercised directly by the device proof.

The companion's explicit diagnostic session freezes ROIs around a fresh, clear, confirmed settled layout. Background, playback/source changes, decoder/calibration invalidation and table editing end collection. Session completion disposes ROI history after the worker exits. No user-facing tracking switch is added before real-source accuracy/performance acceptance. Opt-in Lab diagnostics support `POST /motion-feed?enabled=1&hz=30`, explicit disable and read-only motion metrics; ordinary production has no such endpoint.

## Checked evidence and limits

- [Native ROI proof](evidence/o02-roi-motion.json): a controlled 2×1-pixel translation is measured at approximately 2.00001/1.00001 pixels, with source-time velocity around 60/30 pixels per second. Stationary texture, occlusion, reset, cancellation and a whole-image crop that must retain its borrowed source all pass. Synthetic native bitmaps establish those cases, not real ball accuracy.
- [Physical feed proof](evidence/o02-motion-feed.json): source-paired loopback H.264 TS with a translating hash-texture region; 15/30/60 Hz requested acquisition, one-region flow, a repeated sixteen-region workload and an injected 100 ms worker delay. Every run drains active/pending ownership without worker/scope errors. [APK/fixture provenance](evidence/o02-motion-provenance.json).
- [Initial benchmark](evidence/o02-motion-baseline.json): per-point JNI reads produced one-region worker p95 about 27.5 ms at 30 Hz. The final 30 Hz experiment measures worker p95 about 8.6 ms after bulk reads. These are short sequential runs with warm-up/scheduling variation, not a controlled sustained A/B performance acceptance.
- Pure Core checks prove the two-image bound, exact disposal, overload replacement, native candidate retention, source/generation fences, source-time gaps, stale/cancel/failure behavior and late-return suppression. Agent UI checks and signed test/Lab/production/retained build gates are recorded in [delivery evidence](evidence/o02-motion-delivery.json).

## O02.05 reduced-resolution ROI readback experiment — 8 October 2026

The opt-in O02 motion feed now asks `TextureView` for a 960×540 bitmap from its 1920×1080 surface. Android documents that `getBitmap(Bitmap)` scales surface content to fit the supplied bitmap. The exact paired surface timestamp, source PTS, decoder dimensions and freshness checks remain attached to the original decoded frame. Only the 16 motion ROIs use the smaller bitmap; their sample regions scale with it, and reported displacements/velocities are converted back to decoded-source pixel units. The normal detector and table-verification readers keep the default full-resolution copy. Capture schema 5 includes the actual motion-analysis image dimensions.

The follow-up [30-second capture](evidence/o02-live-gap-half-readback-20261008.json) verified a 960×540 analysis image paired to 1920×1080 decoded frames. On the sequential full-size and half-size runs, one-second acquisition P95 fell from 25.18 ms to 9.20 ms and worker P95 from 54.68 ms to 20.79 ms. Processed cadence improved slightly from 23.69 to 24.25 Hz, but continuity did not: the half-size run had six resets versus five, and its largest gap grew from 136.5 ms to 166.7 ms. All six gap records still had slower acquisition than paired ROI worker time. Exact candidate availability remained clear; the source continuity limit is still 125 ms. This short sequential comparison supports the smaller bitmap as a cost reduction, but it does not establish better continuity or moving-ball accuracy.

The final Release Performance Hybrid build succeeded with zero errors and nine warnings, and the updated Lab package installed and opened on Pixel 11 Pro XL. No tests were run. O02.05 remains open. The next bottleneck check should measure main-thread scheduling against TextureView update callbacks; the current periodic poll can still miss several decoder frames even when the smaller ROI worker is faster. Do not relax the continuity gate.

## O02.05 poll and TextureView timing trace — 8 October 2026

The motion diagnostic now records main-thread queue delay and duration for each candidate poll; candidate frame/source identity; TextureView update count and age at candidate and image read; exact candidate-to-read frame/source deltas; initial read queue delay; and the time spent in native `TextureView.getBitmap`. Each over-threshold source gap carries the same timing and pairing fields. This should distinguish UI-thread wait, texture-update timing, and bitmap-copy cost while retaining exact source timestamps and the existing 125 ms continuity limit. Capture schema 6 carries these values; it saves no camera images and does not change detector, verification, or observation policy.

The updated [30-second capture](evidence/o02-live-poll-texture-timing-20261008.json) completed with 29 one-second samples across a 29-second span. The decoded source remained 1920×1080 and motion ROIs used 960×540. Between the first and last snapshots, the player reported 875 decoded-frame callbacks and 822 TextureView updates; the feed acquired and processed 701 frames (24.17 Hz), replaced none, and recorded 27 copy retries. There were no stale frames, acquisition failures, scope rejections, or worker failures. Seven gap records were collected; the gap counter was already one in the first sample and reached seven in the last. Every recorded interval was 133.344–133.356 ms, with a decoder frame-ID delta of four against the unchanged 125 ms reset threshold.

The gap details identify intermittent main-thread queueing. Candidate checks waited 1.08–92.77 ms to run, while the metadata probe itself took only 0.13–0.33 ms. The read callback then waited 0.20–34.75 ms; the native bitmap copy took 3.06–20.43 ms, and its paired ROI worker took 2.48–11.70 ms. Between the candidate check and acquired image, the frame ID advanced by one to three (33–100 ms). Candidate texture age reached 93.1 ms, while the acquired image's last TextureView update was 6.8–30.7 ms old. The update counter advanced two to three times across each gap-associated processed interval, compared with four decoder frame IDs.

Across one-second metric snapshots, P95 candidate queue delay was 15.9 ms and probe execution 0.29 ms; read queue delay was 30.1 ms, bitmap copy 14.0 ms, acquisition 62.7 ms, worker 15.8 ms, and result age 562.7 ms. These are sampled snapshot percentiles, while the per-gap ranges above are event measurements. This points to intermittent main-thread waiting, plus readback cost, as a substantial source of missed source intervals; the short ROI worker is not the main cost in the recorded gap events. The decoder-to-TextureView count difference also shows that released frames do not map one-for-one to observed texture updates in this run.

Next, coalesce the candidate check and exact-timestamp bitmap read into one main-thread dispatch to remove the extra queue handoff and measure the same stationary case again. Keep source-time pairing, the 125 ms continuity limit, and detector/verification paths unchanged. O02.05 remains open; this run does not establish moving-ball accuracy or prove that queue coalescing alone closes the gap.
