# Shared table scene (T01)

`TableScene` is an immutable, bounded render contract for image paths, selected-path emphasis, ball/pocket/ghost markers, short anchored notes, an upright caption and an optional score display. Points use normalized original-image coordinates. Marker radius is a fraction of source image height. Scores are display content only; G01-G05 must supply the real ledger before production publishes scores.

The native `TableSceneOverlay` validates the contract, accepts only increasing revisions for the current player's media generation and drops expired content. Playback changes reset the scene; explicit clear keeps the revision watermark so a delayed publication cannot revive it. The producer must validate its authoritative table version and clear on table/camera/calibration/group changes; T02 will wire that coordinator boundary. A render contract does not itself validate shot geometry or authorize camera operations.

Phone geometry uses the actual video texture matrix, including portrait/framing. Text renders in a separate upright pass. The landscape encoder copies only the video surface, then draws the same scene snapshot with its own mapping. It never captures the Activity window, MAUI/Blazor view, sheet, key editor or Android controls. Android's [TextureView bitmap API](https://developer.android.com/reference/android/view/TextureView#getBitmap(android.graphics.Bitmap)) copies the underlying surface texture into the specified bitmap; the physical check separately confirms raw landscape video and corresponding portrait markers.

Every captured encoder frame carries scene version, media generation, table version and the player's source position with its reusable bitmap. A bounded timestamp map associates this metadata with actual codec output. `/status` reports `encodedFrame` and the latest drawn `phoneFrame`, rather than labelling the current scene as an already encoded frame. Player position is the local ExoPlayer period position, **not** the camera's authoritative recording timeline or a measured shot timestamp. HLS buffers the TV presentation, so this verifies scene identity and mapping, not simultaneous phone/TV pixels.

The existing candidate publication/cycle remains compatible through `setOverlay`. Its producer, freshness, settlement, confirmation and overlap checks are retained. T02 replaces product touch flows with real scene commands; T01's renderer does not invent candidates or match results.

## Device check without table lighting

The separate SkyEye Lab has Show scene check / Clear scene check under Lab checks. It overlays fixed geometry and explicitly labelled Demo A / Demo B scores for 60 seconds. This check requires a playing live feed but no host, ball detection or table lighting. It is hidden in production. It rejects a wrong media generation and duplicate revision using the actual Android publication gate before encoding the scene.

On 4 October, Pixel 11 renders versions 1 and 2 over the dim mounted Pixel 10 feed. The 960x540 decoded relay frame shows corresponding geometry, upright caption/note and demo score. Native metrics report matching phone/encoded version 2, media generation 4, two paths and three markers. A phone screenshot with the controls sheet open and the corresponding decoded landscape segment establish that sheet/key setup controls do not enter the encoded picture. The user confirms the demo overlay appears on the physical TV. After expiry, phone/encoded metrics both show version 0 and zero paths/markers while video continues.

Home/return clears the scene, disposes its relay and switches the receiver back to the raw camera feed only when that relay still owns receiver content. Pixel then reports TV playing live camera. Camera capture remains independent and Active; no clip is saved. The production in-place update retains UID/storage; build and installed provenance are in `evidence/shared-table-scene.json`.

Limits: composition still needs a visible companion; background falls back to raw camera. The encoder remains silent, 960x540, nominal 10fps, two reusable bitmaps and one pending frame, with bounded segments. Receiver buffering is observed during warm-up and intermittently during this short check; long-session stability/latency remains X02. Dark-condition ball accuracy is not established by a demo scene. Recorded lighting/darkness fixtures can run while the real table lights are off, and are regression evidence rather than a new accuracy dataset.
