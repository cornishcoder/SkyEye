## Separate correctness/performance follow-ups

Track these as bounded fixes under the indicated missions, with reproductions before tuning:

1. **O02 — pixels/PTS pairing.** `PlayerTableFrameSource.ReadAsync` calls `SnapshotForAnalysis` and then `ObservationFrameMetrics`; the latter chooses a released-frame timestamp. There is no atomic receipt proving those pixels correspond to that PTS. Prove pairing with labelled frame IDs and return pixels + actual source PTS together. Retain TS wrap/clock conversion, source identity and generation fencing. This is a risk found in inspection, not an observed timestamp error.
2. **O03 — monotonic boundaries.** `TableTracker` measures still-layout duration with `CapturedAt`; the frame source estimates that wall time from age. Retain UTC for display/audit but use differences in mapped source PTS for motion, velocity and settlement. Test wall-clock jumps, duplicates, source changes and gaps. The current still gate is not proof of shot-end detection.
3. **O04 — absent cue/black versus advice eligibility.** `VisionAnalyzer` flags any layout without exactly one cue and one black as uncertain. A legitimate scratch or black pot can therefore prevent a clear post-shot observation from reconciling. Separate observation quality from game-dependent expected inventory in a small reviewed change; leave advice suppression intact when no valid cue/target exists. Do not assume absence proves a pot. Complete this before claiming scratch/black-pot acceptance.
4. **O01/O04 — boundary blind spots and coverage.** Pocket exclusion, edge margins, pocket-colour review and fixed ball dimensions can hide near-mouth balls or flag overlaps. Label missed/extra circles, dim-table corners and near-cushion positions; characterize the existing T10 coverage gap separately. Correct demonstrated defects without replacing the detector. Full jaw geometry is not already calibrated just because corner pockets are detected.
5. **O02 — expensive readback/native work.** Full-size texture readback, BGR/HSV copies, warp and potentially two Hough passes are reasonable occasional costs. Benchmark ROI/grayscale readback and buffer reuse for frequent tracking. Native calls have limited cancellation granularity; dispose overwritten frame leases and keep work outside the UI thread. Profile before optimizing or assuming new bindings are available.

## Perception phases, identity and geometry

```text
clear settled observation (existing VisionAnalyzer)
    → known layout + track seeds
    → lightweight motion/ROI tracking while shot moves
    → timestamped trajectories + proposed physical events
    → clear post-shot VisionAnalyzer observation
    → reconcile before/tracks/events/after
    → reviewed evidence → SkyEye.GameState
```

O03 owns `AwaitingShot → Moving → Settling → Complete/Uncertain`. New movement during settling returns to Moving. A gap, obstruction or source/calibration change produces uncertainty and reacquisition, never invented continuity. Expensive analysis is triggered for initial/post-shot anchors or documented lost-track recovery, not every decoded frame. Plain viewing stays free of expensive idle perception; an explicitly enabled tracking session may run cheap motion monitoring, with its cost measured.

Proposed track data: `TrackId`, nullable `BallIdentity`, `LastPosition`, `PredictedPosition`, `Velocity`, `Confidence`, `LastSeenSourceTimeUs`, source/clock/generation and calibration version. Keep visual detection IDs, shot-local track IDs and durable game ball IDs separate. Include uncertainty/reason and missing/occluded status. Start with constant-velocity prediction using actual elapsed source time, gated one-to-one association and local image measurements. Add Kalman-style filtering only if it improves held-out results. Smooth, untextured balls may give poor LK features; benchmark flow against simple ROI centroid/template measurements.

Represent positions/velocities in a common calibrated physical table frame. Core analysis currently uses a 2:1 layout (`X/2` maps it to GameState's normalized rectangle); Euclidean distances in that normalized rectangle need the physical aspect restored. Define the mapping once and test it. O04 uses versioned playable bounds, ball diameter, cushion segments/normals and pocket-mouth regions/centres. Measure mouths/jaws or mark their approximations explicitly; do not borrow today's calibration for historical footage. Convert camera pixels at the adapter boundary. Simulation later adds measured SI dimensions rather than treating normalized coordinates as metres.

If same-colour candidates cross, gates overlap or evidence is lost, retain alternatives/unresolved mapping. Reacquire with local re-detection, then a bounded full settled observation if needed. A prediction is not a sighting and cannot extend `LastSeen` or confirm a pot.

## O04.01 — Inventory-aware association from last-seen positions

**Goal:** use recent, source-timed ball positions and the supported game's maximum inventory to associate detections across frames, distinguish stationary balls from plausible movement, and reduce duplicate, shadow and sunlight-pattern detections. This is the first bounded O04 association slice; it does not add a second game ledger or change the detector by itself.

**Inventory semantics:** distinguish the ruleset's maximum ball counts, a clear settled layout observed in this session, and per-frame sightings. A maximum is a hard upper bound, not an exact expected count. Only an accepted/reviewed event may change canonical in-play or pocketed state. A ball missing from a frame remains unseen/occluded/lost/uncertain according to evidence; its old position is never emitted as a current observation and absence alone does not prove a pot.

**Track record:** maintain session-scoped `TrackId`, optional verified `BallIdentity`, last confirmed calibrated table position, last-seen source PTS, velocity estimate when timing and matches support it, appearance/class evidence, association quality, motion state, visibility/loss state and uncertainty reason. Keep detection IDs, track IDs and GameState ball identity distinct. Expire or invalidate tracks on source, generation, calibration or timeline discontinuity. Do not give visually indistinguishable same-colour balls durable identities unless the sequence supports a unique, reviewed mapping.

**Association:** retain the raw candidate detections and their feature scores. Generate one-to-one detection-to-track assignments with gates for elapsed source time, plausible displacement, appearance/class compatibility and table geometry. Use the ruleset maximum to reject globally impossible excess assignments only when candidate evidence permits; never force a low-quality candidate to fill an inventory slot. If more than one assignment remains plausible, surface ambiguity and keep the track unresolved. A stale track can seed a local search or explain a possible movement, but cannot count as visible.

**Movement:** compare associated, fresh positions in calibrated table coordinates over mapped source time. Establish stationary noise and a movement deadband from labelled stationary/light-change sequences, then use hysteresis for `stationary`, `moving`, `settling` and `uncertain`. Illumination change, camera interruption, weak ROI texture, occlusion, crossing, a large source-time gap or calibration change must reduce confidence or trigger reacquisition rather than manufacture movement or continuity. O03 remains the owner of shot boundaries and settling lifecycle.

**Delivery steps:**

1. **O04.01a — Freeze the data contract and cases.** Use O01's identity/visibility labels and O09/O08 lighting samples; add reviewed labels only where the current corpus cannot distinguish a real ball from a false candidate or record a ball's last visible position. Include blind-pattern transitions, stationary balls under changing light, missed/extra detections, slow movement, temporary hiding, crossing same-colour balls, pocket approach and source/calibration resets. Freeze session-grouped development/holdout splits before tuning.
2. **O04.01b — Deterministic offline association [evaluator implemented; real evaluation open].** The `SkyEye.Observation.Workbench association` command consumes one frozen Development or Holdout detector output and uses calibrated table coordinates, source PTS, last-seen gated matching, a configurable ruleset inventory ceiling, explicit ambiguity abstention and separate predicted/ground-truth movement thresholds. It reports per-session/per-tag detector misses/extras, track continuity/identity changes, inventory conflicts, movement confusion and coverage. Replay the same candidate with different association/movement parameters on Development; hold ground-truth movement thresholds fixed. The checked-in seed has no real timed shots, so accuracy/threshold conclusions remain open. Future work may improve motion estimation and add the opt-in per-track visual trace after real sequences justify it.
3. **O04.01c — Diagnostic presentation.** Add an opt-in sequential view of current candidates and tracks: track label, last-seen age/position, current matched or predicted position, motion/visibility state, association quality and unresolved alternatives. Preserve raw frame/candidate access and source PTS so labels can correct the corpus. A predicted marker must be visually distinct from a current detection; this view is diagnostic and read-only.
4. **O04.01d — Bounded live feed.** Only after O02.05 source/PTS, cadence, resource and lifecycle gates, enable the association component on the existing latest-frame-wins motion feed. Keep one active and one replaceable pending frame; do not run full Hough/classification every decoded frame. Use local ROI recovery first and bounded settled-layout analysis only at documented recovery points.
5. **O04.01e — O03/O05 integration.** Supply source-timed motion and uncertainty to O03. Reconcile before-layout, accepted track evidence and clear after-layout through O05 review. Do not directly mutate GameState, infer a pot from a lost track, or use identity guesses to update score, group, turn or advice.

**Acceptance:** replay is deterministic for a fixed recording/configuration; every reported sighting points to a current source frame; no predicted/stale point is presented as observed; the inventory maximum never fabricates missing balls; no silently committed identity swap occurs in the crossing/loss challenge set; ambiguity and reacquisition are explicit. Report recall, precision, ID switches/losses, position error and false movement by lighting/motion case on untouched real sessions. Retain the existing proposed O-series target of visible-sample recall ≥90% and centre error p95 ≤0.5 measured ball diameter for supported cases, with zero silently committed identity swaps; these remain targets, not achieved results. Do not claim improvement until O01/O08 held-out evidence and O02.05 device cost gates pass.

## Physical evidence and audio

O04 proposes `ShotStarted`, `ShotEnded`, `BallCollision`, `FirstContact`, `CushionContact`, `PocketApproach`, `BallEnteredPocket`, `CueBallPotted`, `CueBallSettled` and `TableSettled`. These are evidence descriptions, not a claim that each is already a supported GameState input or a referee decision.

- Pocket evidence needs a calibrated mouth-crossing/approach, subsequent disappearance and a compatible clear settled after-layout with resolved identity. A one-frame loss, occlusion or proximity alone stays uncertain.
- Cushion evidence needs compatible boundary geometry plus observed velocity-direction change. Close approach alone is insufficient.
- Collision evidence needs compatible ball separation/approach and velocity changes. If successive contacts fall inside one sampling interval, report a timing interval/ambiguous order; do not fabricate exact first contact.
- Break/rerack is a layout proposal for review, never an automatic new match/frame. A cue ball later reappearing does not erase a scratch without resolving the shot's evidence.

**O06 — optional audio corroboration**, after the visual O04/O05 slice: use the Pixel 10's microphone capture as timestamped transient evidence. The immediate silent live TS path currently carries video only; recorded AAC existing in archives does not prove live audio evidence is available. Begin with recorded PCM/decoded AAC transients and source-time correlation, then justify any bounded live transport extension separately. No large ML classification project or audio-only adjudication.

Retain timestamp clock domain, source timeline/origin, uncertainty and explicit conversion metadata. Camera audio/video alignment must be measured; companion arrival time/UTC must not be compared directly to camera encoder PTS. A visual event near 18.431 s and mapped transient near 18.427 s can corroborate one another only within measured clock/latency uncertainty. Missing/unsynchronized audio must not prevent visual review. Validate with visible/audible contacts and report false corroboration in room noise.

## Feeding the delivered GameState

1. Perception owns bounded high-rate frame/track buffers and a source-scoped evidence bundle: before/after layouts, trajectory samples, event proposals, time intervals, confidence/reasons and immutable references. Keep high-rate samples out of the 10,000-event match journal. Store a bounded durable bundle/manifest when an accepted event needs replay provenance; define retention so accepted references do not silently dangle.
2. Reuse `EvidenceSource` and `GameInputEnvelope` with camera/timeline/generation/calibration/connection, match/frame identity, source PTS, UTC audit time and idempotent input ID. Add explicit clock-domain/interval/reference metadata through a narrow versioned seam where existing scalar PTS is insufficient. Use `ShotStarted/Ended`, `TableObservation`, `TableSettled`, ball evidence and `PossiblePocketEvent` as appropriate.
3. Route inputs through `SubmitGameInput` and the existing serialized coordinator: validate ownership/source/match/frame/version, persist before publish, and consume `SkyEyeState.Game`. Do not mutate game facts from the tracker or UI. Evidence input ordering must respect the domain's source-time watermark; append reconciliation at its actual later time, referencing earlier trajectory samples rather than submitting old timestamps out of order.
4. R01 already infers a pot from a known before-ball, supported approach and missing ball on a clear settled after-table after shot end. It does not yet provide a general pending-review barrier for that complete evidence chain. O05 must stage proposed outcome-producing bundles before submitting them, so an unreviewed proposal cannot commit a pot merely by traversing existing inputs. Acceptance submits a deterministic validated sequence; rejection/ambiguity retains evidence without feeding a committing chain. Rules outcomes still wait for R04/R02.
5. `PossibleCollision` and `PossibleCushionContact` currently return unsupported. O04/O05 add only the required evidence/event representation with JSON/reducer/journal checks; contact data remains non-adjudicating. First-contact/foul rules are separate reviewed consumers. Cue pots use the existing pot event flag rather than a competing scratch ledger.
6. Preserve observed/inferred/player-confirmed/player-corrected provenance and player precedence. Amendments reference accepted events, repair dependent projections and survive rebuild. A simulated reconstruction is an external consumer result; it cannot overwrite canonical observed history.

## Eventual SkyEye.Physics boundary

```text
video/audio adapters → temporal tracking → trajectories/event proposals
    → reviewed canonical GameState + referenced shot evidence
    → pure C# Physics/reconstruction consumers
    → clean/3D replay, comparison, coaching and counterfactuals
```

**PH01 — bounded physical model**, after trustworthy O04/O05 evidence: a pure C# library, deterministic headless simulation, explicit SI units/table parameters, next-event scheduling where practical, rolling/sliding transitions and one ball-ball/cushion slice. Keep numerical root finding or local integration where needed; event-driven architecture is a preference, not a reason to invent closed-form answers for every model. No Android, OpenCV, UI or canonical state ownership. The application maps immutable GameState/evidence into physics request DTOs; GameState never references Physics.

**PH02 — best-fit reconstruction**, after PH01 model validation: consume pre-layout, sampled trajectories, collision/cushion/pocket time intervals and post-layout, estimate bounded initial speed/spin/model parameters, and return a fit with residuals, uncertainty, unsupported cases and model version. Unobserved spin may be non-identifiable; do not promise a unique answer. Actual-versus-predicted presentation labels samples/events **Observed**, fitted parameters/path **Inferred**, and generated trajectories **Simulated**. Future 3D TV replay uses this contract, preserving access to original footage.

**PH03 — replay/coaching/what-if**, after reconstruction fidelity is measured: rerun the same pre-shot state with altered speed or top/back/side spin for softer/stun/screw/right-hand-side questions. Validate English-pool friction, cushion/jaw and pocket geometry before spin/throw coaching. Masse/jump and complex contacts are later extensions. Simulation is never the authoritative account of a real shot or a rule ruling.

**Shared HUD consumers:** [V01-V04](advanced-shot-hud-plan.md) extend the existing semantic scene and independent phone/TV commands. V01/V02 use current geometry without waiting for tracking or Physics. V03 consumes validated PH01 outcomes; V04 consumes trustworthy O04/O05 observed trajectories plus a preserved pre-shot V02/V03 prediction. PH02's fitted reconstruction and PH03's replay/what-if use the same annotations/comparison view, retaining Observed/Inferred/Simulated provenance. V04 does not implement a second tracker, PH engine or C02 coaching pipeline, and need not wait for full fitted reconstruction to compare a supported geometric prediction with observed motion.

**O07 — detector comparison**, separately deferred until O01 ground truth exists: benchmark existing OpenCV/Hough, a small neural detector/segmenter and a hybrid tracker. Report accuracy/false positives/misses, position error/stability, latency, CPU/GPU/NPU, thermal and battery costs on actual devices. Pixel accelerator availability alone is not justification for replacement or LiteRT integration.

## First useful vertical slice and measurable gates

Deliver a clear settled layout → tracked cue/object-ball pot or miss → settled reconciliation → player-reviewed canonical event → correction/reload demonstration. Complete O01/O02 foundations and O03 boundaries, a bounded O04 case and the minimum O05 review seam together; broader collision, scratch, break and crossing accuracy remain subsequent O04/O05 chunks. Audio/physics are not prerequisites.

The following are **proposed initial acceptance targets**, not observed results. Freeze metrics, thresholds and split before opening held-out results; report every numerator/denominator and explicit exclusions. A failing category remains unsupported/uncertain rather than being hidden in a pooled success rate.
